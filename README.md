# Бот «Гости»

Общая картотека гостей для сотрудников в Telegram. Каждый сотрудник работает в личном чате с ботом: добавляет фотографию, телефон, имя, комментарий, статус входа и причину; ищет гостя по имени или телефону; меняет и удаляет карточки. Доступ к общей базе выдаёт единственный администратор с Telegram ID **7011639945**. Сотрудники работают с карточками, но добавлять других работников не могут.

Проект подготовлен для запуска на Bothost. Токен и настройки хранилища задаются в окружении хостинга; настоящие данные гостей хранятся отдельно от репозитория.

## Где хранится база

Хранилище выбирается явно через `STORAGE_BACKEND`. Режим `postgres` хранит карточки, оригиналы фотографий, посещения, историю и доступ сотрудников в отдельной PostgreSQL-базе, например в Supabase. Он подходит для работы бота на Bothost: обновление приложения не заменяет удалённую базу. Подготовка, перенос и резервные копии описаны ниже.

Режим `sqlite` хранит карточки, фотографии и посещения в одном файле `guests.sqlite3` на постоянном диске хостинга. Telegram `file_id` ускоряет повторную отправку фото; сохранённые оригиналы позволяют отправить его снова, если прежний идентификатор перестал работать. При исчезновении базы бот останавливает операции: пустой файл вместо потерянного не создаётся. Только для первого создания новой базы явно задайте `ALLOW_NEW_DATABASE=1`, затем верните `0`. Эта переменная не восстанавливает потерянные карточки.

Сбой PostgreSQL не переключает бота на SQLite. Недоступная, отсутствующая или неподтверждённая картотека блокирует операции до проверки подключения и восстановления.

## PostgreSQL и Supabase: подготовка и перенос

Для рабочего бота используется отдельная ограниченная роль PostgreSQL с доступом только к картотеке. Пароль владельца базы нужен оператору для первоначального создания и переноса; сохранять его в рабочем `DATABASE_URL` бота не следует. Ключи Supabase API не заменяют строку подключения PostgreSQL. Таблицы находятся в закрытой схеме `guest_registry`, с включёнными правилами доступа; права для публичных ролей не выдаются.

Настройки рабочего бота на Bothost:

| Имя | Значение |
| --- | --- |
| `STORAGE_BACKEND` | `postgres` |
| `DATABASE_URL` | Приватная строка подключения ограниченной роли из настроек Supabase |
| `REGISTRY_ID` | Постоянный идентификатор подготовленной картотеки; тот же, что при переносе |
| `DB_SSLMODE` | `verify-full` — проверка сертификата и имени сервера |
| `DB_SSLROOTCERT` | `/app/certs/supabase-prod-ca-2021.crt` — официальный сертификат Supabase, включён в проект |
| `POSTGRES_BACKUP_DIR` | `/app/data/backups` на постоянном диске Bothost |

`BOT_TOKEN` и `ALLOWED_USER_IDS` остаются обязательными. `ALLOW_NEW_DATABASE` не создаёт PostgreSQL-схему и не устраняет ошибки подключения. Обычный запуск проверяет владельца, идентификатор и структуру существующей картотеки; отсутствующая или другая база не заменяется пустой.

Скрипт `migrate_to_postgres.py` читает сохранённый приватный JSON: результат восстановления или полную PostgreSQL-копию. Обёртка должна содержать `state` со всеми шестью разделами картотеки и `sequences` с сохранёнными счётчиками ID. Дополнительный `recovered_totals` хранит подтверждённые остаточные итоги прошлых посещений. Исходный файл открывается только для чтения. Сами JSON-копии содержат персональные данные и фотографии: храните их вне репозитория.

1. Остановите бота. Сохраните свежую копию действующих данных. Если восстановление объединяет старые материалы с текущей базой, сначала подготовьте отдельный проверенный JSON с сохранением актуальных изменений. Скрипт не объединяет конфликтующие карточки автоматически.
2. Выполните локальную проверку. В командах замените `N` точным ожидаемым количеством карточек:

   ```text
   python migrate_to_postgres.py --source private/restored.json --expected-guests N
   ```

   Без `--apply` соединение с базой не открывается. Проверяются все разделы, фотографии, связи, счётчики и восстановленные итоги. Результат содержит только количества и контрольные суммы.
3. Для записи задайте оператору приватные `POSTGRES_MIGRATION_URL` и `REGISTRY_ID`. Используйте роль владельца схемы: ограниченная роль бота не может восстанавливать счётчики. Для первой подготовки создайте отдельную рабочую роль без прав администратора и `BYPASSRLS`, затем укажите её имя в `POSTGRES_RUNTIME_ROLE`. Пароли вводите в закрытых настройках окружения, не в общих командах или Git.
4. Для совершенно нового назначения выполните:

   ```text
   python migrate_to_postgres.py --source private/restored.json --expected-guests N --apply --initialize
   ```

   `--initialize` создаёт только отсутствующую схему и отказывается заменять существующую. Если пустая схема уже подготовлена оператором, используйте `--apply` без `--initialize`. Ожидаемое число гостей обязательно при записи. Импорт выполняется один раз, только в полностью пустое назначение; затем все разделы, байты фотографий, восстановленные итоги и счётчики читаются обратно и сравниваются с источником. Ошибка проверки требует разбора результата, а не повторного запуска поверх данных.
5. После подтверждённой проверки настройте рабочий `DATABASE_URL` ограниченной роли, сохраните тот же `REGISTRY_ID`, запустите один экземпляр бота и проверьте карточки, доступ сотрудников, таймер и Excel. До завершения импорта бот не запускайте: он сохраняет доступ и профили сотрудников, после чего назначение перестаёт быть пустым.

Восстановление по сообщениям Telegram ограничено сохранившимися доказательствами. У некоторых карточек могут отсутствовать оригинальные фото; они показываются текстом с кнопками, а фотографию можно добавить через «Изменить». Новая карточка по-прежнему требует фото. Подтверждённые общие количество посещений и время могут быть восстановлены отдельно от точных дат: они входят в общие итоги и Excel, а статистика за день, неделю и месяц учитывает только известные датированные посещения. Это не подтверждает полноту неизвестной истории и не создаёт вымышленных визитов.

### Резервные копии PostgreSQL и ограничения Free

Работающий PostgreSQL-бот делает полную JSON-копию при запуске и затем каждые 6 часов в `POSTGRES_BACKUP_DIR`. В неё входят оригиналы фотографий, все карточки, посещения, история, сотрудники, доступ, отметки напоминаний, восстановленные итоги и счётчики ID. Готовый файл публикуется целиком под новым именем. Копии сохраняются без автоматического удаления: контролируйте свободное место. Размер памяти для экспорта растёт вместе со всей картотекой, включая фотографии.

Каталог копий должен находиться на постоянном диске Bothost, отдельно от Supabase. Файлы в обычном каталоге контейнера могут исчезнуть после обновления или пересоздания. Регулярно скачивайте JSON-копии и держите дополнительный экземпляр вне Bothost: потеря всего диска хостинга уничтожит и локальные копии. Эти файлы защищайте как основную базу. Периодически проверяйте восстановление отдельной копии в новую тестовую картотеку через тот же скрипт и полное обратное сравнение.

У Supabase Free [нет автоматических резервных копий провайдера](https://supabase.com/kb/faqs/platform/free-plan-backups); проект с низкой активностью [может быть приостановлен после 7 дней](https://supabase.com/docs/guides/platform/free-project-pausing). Следите за уведомлениями владельца проекта, доступностью бота, свободным местом и успешным созданием копий. Автоматическая копия требует работающего бота, доступа к базе и диску. Отдельная база и резервные копии снижают риск потери, но не гарантируют непрерывную работу или полное восстановление при любом сбое.

## Количество гостей, чёрный список и Excel

В главном меню доступны три отчёта для разрешённых сотрудников в личном чате:

- **«Всего гостей»** (`/count`) показывает число всех карточек, включая гостей с закрытым входом.
- **«Чёрный список»** (`/blacklist`) присылает полный список карточек со статусом **«Вход закрыт»**: имя, телефон и причина. Если список длинный, он приходит несколькими сообщениями без ограничения числа гостей.
- **«Выгрузить в Excel»** (`/export`) отправляет один `.xlsx` с листами **«Гости»** и **«Посещения»**. В нём все карточки, фотографии в виде миниатюр, телефоны, статусы, причины, комментарии, накопленное время, текущие визиты, даты и история посещений. Телефоны и пользовательские тексты сохраняются текстом, без выполнения формул. Даты указаны по Москве, длительности отображаются и свыше 24 часов. Пустая база тоже даёт корректный файл с заголовками.

Отчёты всегда включают выбранное основное хранилище: PostgreSQL или SQLite из `DB_PATH`. Дополнительные SQLite-базы с совместимой схемой картотеки можно явно подключить переменной `EXTRA_DB_PATHS` — JSON-массивом путей, например:

```text
EXTRA_DB_PATHS=["/app/shared/club2/guests.sqlite3","/app/shared/club3/guests.sqlite3"]
```

Если дополнительных баз нет, не задавайте переменную или укажите `[]`. Пути должны быть доступны боту на сервере. Дополнительные базы участвуют во всех трёх отчётах и читаются без изменения; добавление, поиск и редактирование карточек по-прежнему работают в основной базе. Старые совместимые базы без статуса или посещений читаются без миграции: статус считается открытым, причина и история — пустыми.

Один и тот же файл по нескольким путям учитывается один раз. Карточки из разных баз сохраняются отдельными строками с номером и названием источника, даже если их ID или телефоны совпадают. Резервные копии и случайные файлы автоматически не подключаются. Если любая подключённая база отсутствует, повреждена или несовместима, весь отчёт отменяется — частичная выгрузка не выдаётся. Внутри каждой базы данные берутся из одного согласованного снимка SQLite; единой транзакции между независимыми файлами нет.

Excel формируется в памяти и отправляется только запросившему сотруднику. Полные оригиналы фото обрабатываются по одному и заменяются миниатюрами для ограничения памяти. Если старое фото повреждено, карточка сохраняется в выгрузке с отметкой об отсутствии доступной миниатюры. Файл больше лимита отправки Telegram не обрезается: бот сообщает об ошибке. Для появления новых кнопок после обновления отправьте `/start`.

## Статистика, гости в заведении, журнал и напоминания

- **«Статистика»** (`/stats`) показывает посещения, уникальных гостей, общее время и топ 5 посетителей. Кнопки **«День»**, **«Неделя»**, **«Месяц»** выбирают текущий календарный период по Москве (UTC+3): с полуночи, с понедельника или с первого числа до момента запроса. Посещения и уникальные гости считаются по началу визита; общее время включает только пересечение всех визитов с выбранным периодом, в том числе начатых раньше и ещё активных. Статистика включает явно подключённые базы, как Excel. Она отражает посещения действующей картотеки: удаление карточки удаляет её посещения.
- **«Сейчас в заведении»** (`/present`) показывает всех гостей основной базы с активным таймером, по восемь на странице, от самого долгого визита к самому новому. У каждого есть время прихода, текущая длительность, кнопки карточки и **«Стоп»**. **«Обновить список»** обновляет показания; старое сообщение само не меняется. Кнопка остановки привязана к конкретному визиту и не может остановить следующий визит того же гостя.
- **«История изменений»** (`/audit`) доступна из главного меню и отдельно из карточки. Записываются создание, редактирование, удаление, запуск и остановка таймера, числовой ID сотрудника и время. Имена и `@username` сотрудников запоминаются из разрешённых сообщений; если имя ещё неизвестно, показывается Telegram ID. Изменённые поля содержат значения до и после. В списке длинный текст сокращён, кнопка **«Подробнее»** открывает полную запись. Вместо байтов фотографии сохраняется только отметка о фото. Запись фиксируется в одной транзакции с изменением, неудачные операции не добавляют событий. Журнал начинается с установки функции: прошлые изменения не выдумываются. После удаления карточки журнал сохраняется и может содержать прежние имена, телефоны, комментарии и причины.
- **Напоминание о таймере** приходит после 24 часов активного визита сотруднику, который нажал «Старт». Если его ID уже исключён из доступа, выбирается сотрудник с наименьшим разрешённым ID. Проверка выполняется сразу после запуска и каждые пять минут. Сообщение содержит имя, телефон, время прихода, длительность, кнопки карточки и **«Стоп»**. Таймер автоматически не останавливается. Успешная отправка отмечается в выбранном хранилище и повторно для этого визита и получателя не отправляется после обычного перезапуска. Ошибка Telegram оставляет напоминание для следующей проверки; авария ровно между принятой отправкой и сохранением отметки может вызвать повтор.

Если Telegram ограничивает частоту отправки напоминаний (429), текущая пачка прекращается, а следующая проверка откладывается как минимум на указанный Telegram срок. Между обычными отправками выдерживается пауза. Уже отправленные напоминания сохраняют свои отметки.

Все эти функции доступны только разрешённым сотрудникам в личном чате. Журнал, имена сотрудников и отметки напоминаний лежат в той же постоянной базе и включаются в её резервные копии. При обновлении существующей базы перед добавлением таблиц автоматически создаётся полная копия в `data/backups/guests-before-activity-…sqlite3`. Новые таблицы не изменяют старые карточки и посещения. Для появления новых кнопок отправьте `/start`.

## Статус входа и причина

При добавлении гостя после комментария выберите кнопкой **«Вход открыт»** или **«Вход закрыт»**, затем введите причину либо нажмите **«Без причины»**. Оба поля видны в предпросмотре и сохранённой карточке всем сотрудникам. Длинные причины и комментарии бот отправляет отдельными сообщениями без обрезки.

В карточке нажмите **«Изменить» → «Статус входа»**, чтобы выбрать новый статус и причину. Они сохраняются вместе после ввода причины; отмена не меняет карточку. **«Изменить» → «Причина»** меняет только причину; **«Без причины»** или `-` очищает её. Максимум — 3000 символов. Если карточку уже изменил другой сотрудник, откройте её заново перед редактированием.

Статус служит отметкой для сотрудников. Изменение статуса не запускает и не завершает посещение: кнопки таймера работают отдельно.

При обновлении базы существующим гостям добавляется **«Вход открыт»** и пустая причина. Перед изменением схемы создаётся согласованная резервная копия в `data/backups/guests-before-entry-status-*.sqlite3` (для самой старой схемы используется копия `guests-before-visits-*.sqlite3`). При ошибке резервного копирования миграция не начинается. Фотографии, карточки и вся история посещений сохраняются.

## Время посещений

Откройте карточку через поиск. Когда гость приходит, нажмите **«Старт»**; когда уходит — **«Стоп»**. Завершённое посещение сохраняется и добавляется к общему времени. Карточка показывает текущий визит, общее время (включая идущий визит) и число завершённых визитов. **«Обновить время»** заново показывает актуальное значение; сообщение с карточкой само по секундам не меняется.

Таймер общий для всех сотрудников: один может начать посещение, другой — завершить. Повторное нажатие или старая кнопка не создают второй таймер и не останавливают следующее посещение. Редактирование данных гостя не сбрасывает время. **«История посещений»** показывает по пять визитов с началом, завершением и длительностью; даты отображаются по Москве (МСК).

Время начала и завершения хранится в UTC в базе. Перезапуск и обновление бота не прерывают отсчёт: посещение продолжается до нажатия «Стоп», в том числе во время остановки бота. Автоматического завершения или ограничения длительности нет. Каждый завершённый визит учитывается с точностью до целых секунд; часы могут превышать 24.

При первом обновлении старой базы бот сначала сохраняет её согласованную резервную копию в `data/backups/guests-before-visits-*.sqlite3`, затем добавляет таблицу посещений. Если копию создать не удалось, обновление схемы не начинается. Существующие карточки и фотографии сохраняются; их накопленное время начинается с нуля.

На Bothost задайте `DB_PATH=/app/data/guests.sqlite3`. Документация платформы описывает `/app/data` как постоянное хранилище между обновлениями. Перед вводом настоящих гостей обязательно проверим это в вашем аккаунте: создадим тестовую карточку, перезапустим бота и обновим код, затем снова найдём её. [Хранение базы](https://bothost.ru/docs/database-storage), [проверка сохранности после обновления](https://bothost.ru/docs/sqlite-data-lost).

Локально без настройки пути база находится в `data/guests.sqlite3`. Переменная `DB_PATH` имеет приоритет над `DATA_DIR`. Незавершённый ввод карточки хранится в памяти: после перезапуска его нужно начать заново. Уже сохранённые карточки остаются в базе.

## Подготовка доступа

1. В [@BotFather](https://t.me/BotFather) создайте нового бота командой `/newbot`. Сохраните токен отдельно от проекта.
2. При первоначальном запуске укажите `ALLOWED_USER_IDS=7011639945`. Код этой установки закрепляет администратором только этот ID. Переменная `ADMIN_USER_ID` не меняет владельца.
3. Администратор отправляет боту `/start`, нажимает **«Сотрудники» → «Добавить сотрудника»** и вводит числовой Telegram ID работника. Работник предварительно получает свой ID командой `/myid`. После проверки числа администратор подтверждает выдачу доступа. Работник отправляет `/start` и сразу может заполнять общую базу; перезапуск и изменение настроек хостинга не нужны.

Команда `/staff` открывает панель сотрудников, `/addstaff` начинает добавление. Кнопки, команды и подтверждения управления доступом проверяют ID администратора на сервере при каждом действии. У работников этих кнопок нет; поддельная или пересланная кнопка прав не даёт. Новые сотрудники имеют обычные права картотеки: создание, поиск, изменение, удаление, посещения и отчёты. Число в подтверждении выдачи доступа нужно сверить с сотрудником; телефон и `@username` не заменяют Telegram ID.

Права лежат в `employee_access` выбранной основной базы; администратор закрепляется в `registry_meta` для PostgreSQL или `access_settings` для SQLite. Таблица имён `staff`, первое обращение к боту и `/myid` не открывают доступ. Администратор закрепляется при инициализации; другой ID владельца для уже настроенной базы отклоняется. При обновлении список из старого `ALLOWED_USER_IDS` переносится в работников один раз, кроме самого администратора и старого служебного значения `9007199254740992`. Повторные запуски и правка переменной не добавляют работников заново. Права сохраняются в резервных копиях вместе с карточками. При обновлении старой SQLite до добавления таблиц создаётся копия `data/backups/guests-before-access-…sqlite3`; карточки, фото, посещения и журнал не меняются.

Команда `/myid` доступна в личном чате даже пользователю вне списка и показывает только его собственный ID. Остальные действия закрыты. В групповых чатах работа с карточками запрещена. Без токена или непустого корректного списка ID бот не запускается.

## Запуск на Bothost

1. Используйте репозиторий [MAYER-Ti/guest_registry_tg_bot](https://github.com/MAYER-Ti/guest_registry_tg_bot). Файлы `main.py`, `storage.py`, `config.py` и `requirements.txt` должны лежать в его корне.
2. В Bothost создайте Telegram-бота, подключите репозиторий и выберите его ветку. Для приватного репозитория настройте доступ по [инструкции Bothost](https://bothost.ru/docs/git-repository-access).
3. Укажите библиотеку aiogram и главный файл `main.py`. Можно включить «Использовать собственный Dockerfile» — он уже подготовлен под Python 3.12. При этом команду запуска задаёт Dockerfile. [Точка входа](https://bothost.ru/docs/main-file-entrypoint), [свой Dockerfile](https://bothost.ru/docs/custom-dockerfile).
4. Добавьте переменные окружения:

   | Имя | Значение |
   | --- | --- |
   | `BOT_TOKEN` | Токен вашего бота из @BotFather |
   | `ALLOWED_USER_IDS` | `7011639945`; новые сотрудники добавляются администратором в боте |
   | `DB_PATH` | `/app/data/guests.sqlite3` |

   Для PostgreSQL сначала выполните подготовку и перенос выше, затем укажите `STORAGE_BACKEND=postgres`, `DATABASE_URL`, `REGISTRY_ID`, настройки TLS и каталог резервных копий. Для существующей SQLite оставьте `ALLOW_NEW_DATABASE=0`; для намеренно новой базы разрешите создание только при первом запуске.

5. Выполните деплой, проверьте журнал запуска и отправьте боту `/start`. До завершения переноса не запускайте бот на пустом PostgreSQL-хранилище: запуск и первые обращения сохраняют доступ и профили сотрудников, после чего импорт в него будет отклонён.
6. Проверьте сохранение тестовой карточки после перезапуска **и обновления из Git**, затем начинайте работу с настоящими карточками.

Бот получает сообщения через long polling. Домен и webhook для этого проекта не нужны. Запускайте только один экземпляр с одним токеном: одновременная работа локального бота и Bothost вызывает конфликт получения сообщений.

`.env.example` — образец переменных. Файл `.env` автоматически не читается: на Bothost используйте настройки окружения. В GitHub отправляется код. Токен, база с фотографиями и резервные копии исключены через `.gitignore`; перед загрузкой всё равно проверьте список файлов.

## Резервные копии и восстановление SQLite

Этот раздел относится к `STORAGE_BACKEND=sqlite`. `backup.py` сохраняет SQLite; для PostgreSQL используйте полные JSON-копии и порядок восстановления выше.

Резервная копия содержит карточки, фотографии, историю посещений и активные таймеры. Скрипт использует механизм резервного копирования SQLite и подходит для работающего бота; токен ему не нужен:

```powershell
python backup.py backups/guests-2026-10-08.sqlite3
```

На Bothost выполните команду из каталога `/app`, указав файл внутри постоянного хранилища:

```text
python backup.py /app/data/backups/guests-2026-10-08.sqlite3
```

Выбирайте новое имя для каждой копии. Скрипт откажется перезаписать существующий файл и не создаст пустую базу, если исходная база не найдена. Регулярно скачивайте копии и храните их отдельно от аккаунта хостинга: копия на том же сервере не защищает от потери всего хранилища.

Для восстановления остановите бота, сохраните текущую базу и замените её выбранной копией по пути из `DB_PATH`. Старые служебные файлы `guests.sqlite3-wal` и `guests.sqlite3-shm`, если они остались после остановки, перенесите вместе со старой базой: их нельзя оставлять рядом с восстановленной копией. Запустите бота и проверьте карточку с фотографией. Восстановление возвращает всю картотеку к моменту копии.

Удаление убирает карточку, её посещения и активный таймер из действующей картотеки после подтверждения. Копии могут остаться в резервных файлах и ранее отправленных сообщениях Telegram. Обращайтесь с ними так же внимательно, как с основной базой, и удаляйте старые копии, когда они больше не нужны.

## Проверка перед рабочим запуском

- Все четыре сотрудника видят общую тестовую карточку и могут найти её по имени и телефону.
- Изменение фотографии, телефона, имени и комментария видно остальным сотрудникам.
- Отмена удаления оставляет карточку; подтверждённое удаление убирает её из поиска.
- Пользователь вне списка не получает карточки; групповой чат не получает карточки даже от разрешённого сотрудника.
- После перезапуска и обновления из Git тестовая карточка и фотография сохраняются.
- Таймер тестового гостя продолжает отсчёт после перезапуска и обновления из Git; другой сотрудник может завершить визит, после чего время видно в общей сумме и истории.
- Резервная копия успешно восстанавливается в отдельную тестовую базу.

Сначала проверяйте эти действия на вымышленных данных. Эта версия панели позволяет просматривать и добавлять сотрудников; отзыв доступа отдельной кнопкой пока не реализован. Удаление ID из `ALLOWED_USER_IDS` не отзывает уже сохранённые права.
