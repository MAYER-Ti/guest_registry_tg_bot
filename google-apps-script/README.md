# Google Таблицы и закрытый архив фотографий

Бот работает на Bothost, а карточки, посещения, история и доступ сотрудников хранятся в Google Таблице владельца. Оригиналы фотографий находятся в отдельной закрытой папке Диска. Apps Script принимает подписанные запросы бота и проверяет владельца, структуру, версии карточек и доступ сотрудников. Администратор — Telegram ID `7011639945`.

Режим не требует платной базы. Действуют [квоты Apps Script](https://developers.google.com/apps-script/guides/services/quotas), [лимиты Sheets API](https://developers.google.com/workspace/sheets/api/limits) и свободное место аккаунта. Таблица предназначена для небольшой картотеки; на большом объёме нужны отдельная база и иной процесс резервного копирования. Тариф самого хостинга оплачивается отдельно.

## Настройка владельцем

1. Выберите личный Google-аккаунт владельца. Создайте в нём закрытую Google Таблицу из подготовленного пустого шаблона с восемью листами и точными заголовками из `Code.gs`. Также создайте закрытые папки фотографий и резервных копий. Не включайте доступ по ссылке и не добавляйте других читателей или редакторов. Сотрудники получают данные через бота.
2. В этом же аккаунте создайте проект [Google Apps Script](https://script.google.com/). Добавьте `Code.gs` и настройки `appsscript.json` из этой папки. В расширенных сервисах включите **Google Sheets API v4** и **Google Drive API v3**; манифест уже содержит оба сервиса. Drive API проверяет полный список разрешений, включая отдельных пользователей, группы и опубликованный доступ: допустим только владелец. Для собственного стандартного Cloud-проекта оба API также включаются в его консоли.
3. В настройках проекта, **Свойства скрипта**, задайте следующие значения:

   | Свойство | Значение |
   | --- | --- |
   | `REGISTRY_OWNER_EMAIL` | Адрес Google-аккаунта владельца строчными буквами |
   | `REGISTRY_ADMIN_ID` | `7011639945` |
   | `REGISTRY_SPREADSHEET_ID` | ID подготовленной Google Таблицы |
   | `REGISTRY_PHOTO_FOLDER_ID` | ID закрытой папки фотографий |
   | `REGISTRY_BACKUP_FOLDER_ID` | ID закрытой папки резервных копий |

4. Вручную запустите `setup` от владельца. Google запросит разрешения на таблицы, файлы Диска и определение адреса аккаунта. Просмотрите их перед выдачей: доступ к Диску распространяется на аккаунт, а не только на три созданных файла. `setup` проверит владельца, заголовки, пустое назначение и закрытый доступ; защитит листы, скроет служебные данные и создаст приватный `REGISTRY_SECRET`. Секрет остаётся в свойствах скрипта и не выводится в журнал.
5. Опубликуйте проект как **Веб-приложение**, выполняемое от имени владельца, с доступом **Все**. Закрытые файлы при этом не публикуются. Каждый POST требует HMAC-SHA256; знание URL не даёт доступа к картотеке. Используйте рабочий адрес `https://script.google.com/macros/s/…/exec`, а не адрес разработки `/dev`. После изменения кода обновляйте версию развёртывания.
6. В закрытых настройках окружения Bothost задайте:

   ```text
   STORAGE_BACKEND=google_sheets
   SHEETS_ENDPOINT=https://script.google.com/macros/s/DEPLOYMENT_ID/exec
   SHEETS_SECRET=<значение REGISTRY_SECRET из свойств скрипта>
   SHEETS_OWNER_EMAIL=<тот же адрес владельца>
   ALLOWED_USER_IDS=7011639945
   ALLOW_NEW_DATABASE=0
   ```

   `BOT_TOKEN` остаётся в окружении хостинга. Ни секрет, ни токен, ни файлы с данными нельзя помещать в GitHub, URL запроса или общие журналы. `.env` автоматически не читается.

После `setup` ID таблицы и основных папок закреплены в свойствах `REGISTRY_BOUND_*`. Удаление файла, пропажа ID и подмена назначения не создают новую пустую картотеку. Перед запуском выполняется подписанная проверка владельца, администратора и версии схемы. Не удаляйте служебные свойства для обхода ошибок.

## Перенос существующей базы

Назначение должно быть новым: только заголовки и служебные настройки после `setup`. **Сначала перенос, затем первый запуск бота.** Даже при нуле гостей нужно сохранить работников и историю доступа. Импорт в заполненную таблицу не перезаписывает её и завершится отказом.

1. Сохраните полную копию действующей SQLite через `backup.py`. Для окончательного переноса остановите старый экземпляр бота, чтобы после снимка не появлялись новые изменения. Сохраните исходную копию отдельно от хостинга. Не используйте незавершённый файл с непустым соседним `-wal`.
2. Выполните локальную проверку, явно указав ожидаемое число карточек:

   ```text
   python migrate_to_sheets.py --source backups/before-google.sqlite3 --expected-guests N
   ```

   Без `--execute` программа не обращается к Google: проверяет файл и показывает количества записей и SHA-256. При неожиданно пустой копии остановитесь и найдите нужный источник, а не подставляйте `0` ради успешной команды.
3. Настройте Google-переменные окружения и выполните ту же команду с `--execute`. Фотографии предварительно загружаются отдельно, затем карточки и связанные записи сохраняются одной операцией. Исходный файл открывается только для чтения. Сохраняются ID, версии, даты, посещения, история, профили, доступ сотрудников, отметки напоминаний и верхние значения счётчиков. Итог проверяется повторным чтением назначения, включая байты фотографий. Текущая утилита ограничивает исходный экспорт 50 МиБ; больший объём требует отдельного переноса.
4. Переключите единственный рабочий экземпляр на Google только после подтверждённой проверки. Проверьте создание, поиск, редактирование, таймер, Excel, доступ сотрудников, перезапуск и резервную копию на вымышленных данных. Сохраните исходную SQLite как архив.

Если связь оборвалась после отправки импорта, результат может уже находиться в таблице. Не очищайте назначение и не повторяйте перенос вслепую: сначала сравните данные. Повторный импорт в заполненное хранилище отклоняется. Ошибка переноса не изменяет SQLite; предварительно загруженные фотографии могут остаться в закрытой папке.

## Работа и ограничения

Google Таблица используется для просмотра. Правки выполняются через бота: контрольная сумма обнаруживает ручное изменение и удаление строк. Отказ доступа или сбой Google приводит к сообщению об ошибке; данные не подменяются пустой SQLite, отчёт с частичными данными не выдаётся.

Сервер сериализует запросы через `LockService`. Записи, версия карточки, история и журнал повторных запросов сохраняются атомарным `batchUpdate`. Повтор того же подписанного запроса после сетевого сбоя возвращает прежний результат. Если две команды сотрудника опираются на разные версии, устаревшая команда отклоняется. Потеря последнего ответа всё равно требует проверки карточки перед новым действием.

Фотографии неизменяемы, проверяются по SHA-256 и ограничены 10 МиБ. Старые оригиналы, журнал операций, история и резервные копии автоматически не очищаются: это нужно для повторных запросов и восстановления. Следите за ростом объёма. Операции с Google медленнее локальной базы; во время длительной резервной копии другие запросы могут временно получить отказ занятости.

## Резервные копии и восстановление

При работе с Google бот проверяет наличие копии при запуске и каждые шесть часов. За календарный день UTC используется одна завершённая копия: отдельная таблица, архив оригиналов фотографий и `manifest.complete.json`. Фото с одинаковым SHA-256 повторно между копиями не дублируются. Успех отмечается только после проверки требуемых фотографий. При ошибке проверка повторяется через 30 минут, администратор получает предупреждение не чаще одного раза за день в рамках одного запуска.

Копия на том же Google-аккаунте помогает при потере данных хостинга и ошибках в основной картотеке, но не защищает от потери всего Google-аккаунта. Периодически сохраняйте завершённую копию вне этого аккаунта. Excel-выгрузка содержит миниатюры и не заменяет полный архив оригиналов и служебных данных. Удаление архива фотографий может повредить сразу несколько дневных копий. Автоматической политики удаления нет.

Восстановление выполняется в **отдельный новый проект Apps Script и новую пустую таблицу** этого владельца. Укажите новую папку рабочих фото, а папку резервных копий — прежнюю, затем выполните `setup`. Не запускайте на новом назначении обычный бот до восстановления. Через настроенный `SheetsStore` вызовите `restore_backup(manifest_file_id, admin_id=7011639945)`, где ID относится к `manifest.complete.json` нужной копии. Сервер проверяет принадлежность файлов, структуру снимка и хеши фотографий, создаёт новые рабочие оригиналы и восстанавливает записи. Существующее заполненное назначение не перезаписывается.

После восстановления сравните количество карточек, посещений, историю и доступ сотрудников; откройте фотографии и активные таймеры. Только затем переключайте рабочий экземпляр. Такой пробный запуск восстановления нужен до начала постоянной работы: локальные автоматические проверки не подтверждают фактические разрешения и квоты Google.

## Проверки кода

```text
python -m unittest discover -s tests -v
node --test --test-isolation=none tests/test_sheets_server.mjs
```

Python проверяет клиент, отчёты, авторизацию, перенос и отсутствие пустой замены базы. Node запускает Apps Script в имитируемом окружении Google: подпись, повторные запросы, конкурирующие версии, атомарный отказ, фото, полную копию и восстановление. Эти проверки не обращаются к реальным аккаунтам и не отправляют сообщения сотрудникам.
